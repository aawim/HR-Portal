# Position management and HR allowance assessment

Canonical pages:

- `/admin/settings/positions/manage-positions`: create, edit, activate/deactivate, search and filter the shared position catalogue.
- `/admin/settings/positions/overview`: current staff counts and expandable staff lists across the schemes.
- `/admin/settings/positions/position-allowances`: required position allowances. The payroll configuration page links here instead of providing another editor.

The existing `Positions` table remains the single position catalogue. `PositionFrameworkID` references `PF_Frameworks`: `LEGACY` (existing CSC / Non-CSC positions), `NEW_PAY` (government Job Matrix), and `CUSTOM` (Non CSC / Custom). Migration `20261029163000_CustomPositionFramework` adds only the missing custom framework, allocating an unused ID. Existing framework IDs, position IDs and employment records are retained. `PositionMatrixID` links government positions to existing `PF_PositionMatrix` entries; legacy and custom positions leave it null.

`PositionTypes` is a different catalogue from `PF_Frameworks`, not a duplicate table. The inspected database has 190 CSC and 81 Non-CSC positions, all currently linked to `LEGACY`. They are not automatically reclassified. The UI exposes the existing type, rank and classification links for legacy positions, with current-organisation rank/classification selectors. Employment-linked framework/type/rank/classification changes are blocked; use a new position and the approved staff position-change process.

Legacy CSC and custom position basic salaries use the existing `PositionBasicSalaries` table. Each entry has an amount, effective date and operation-log reference. The UI shows valid salary history and appends a new effective-dated amount; it never edits/removes prior entries. A new salary must start after the latest valid record, and amounts are validated as nonnegative with at most two decimal places. The existing SQL float column is preserved for compatibility; transport/input uses decimal. This configures the position salary catalogue, without rewriting `Jobs.BasicSalary`, employee salary snapshots, pay-step history or posted payroll. Government matrix salaries continue to come from the matrix/pay-step scheme and cannot be overridden through this form.

Required position allowances remain framework-independent and use the same canonical Position Allowances page. `SAPWageTypes` remains a shared payroll integration catalogue, with its existing `PrimaryPayrollItemTypeSAPWageTypes`/`SAPExceptions` relationships. This change does not create competing framework-specific wage-type tables or claim to implement a new SAP export. `ServiceTypesAllowedServiceStateTransitions` is retained as a service-state configuration table; it is not substituted for request approval transitions in `RequestTypesAllowedRequestStateTransitions`.

The UI uses the actual framework names and reads existing government definitions from `PF_PositionMatrix`, `PF_JobMatrix` and `PF_JobTitles`. These existing tables are excluded from EF table-creation migrations. It does not invent government grades, pay scales or matrix records. The current database has no `PF_PositionMatrix` entries, so government position creation is unavailable until a valid current-tenant matrix entry exists. This change implements the shared position catalogue and existing matrix selection, not government pay-matrix definition maintenance.

Current-tenant `Positions.Configure` grants position configuration. `Position.Details`/`Staff.Positions.Manage` allow catalogue reads. Only actual superadministrators can edit global positions. A tenant officer cannot edit another organisation's positions, global positions or unscoped shared legacy records. Government matrix selections must belong to the current organisation and be currently effective. A position with employment history cannot change its framework, matrix link or global scope; create a new position instead. Renaming/deactivation preserves staff assignments and their approval history. There is no destructive delete action.

For shared legacy CSC or custom catalogue positions, a superadministrator selects **Global — available to all organisations** in Manage Positions. These records use `IsGlobal = true` and a null `OrganisationId`; active records are available in every organisation's staff enrolment and staff position assignment selectors. Organisation officers may use them through the existing approval flow but cannot edit or convert the shared definition. The position list shows Global / Organisation scope. Government position matrices remain organisation-specific; this catalogue scope does not share another organisation's staffing slots or employment records.

Position allowance rules retain the existing `StaffFinance.Configure` permission. Staff-requested allowance pricing uses the separate `StaffFinance.Assess` permission. Both must be allowed by organisation permission limits and assigned through the existing permission/User Group process; this migration does not grant staff or organisations access automatically.

Migration `20261029151054_PositionFrameworksAndAllowanceAssessments` conditionally adds the two position link columns only if absent and preserves existing values. It creates `AL_AllowanceAssessments`, adds the two permissions and installs an append-only assessment trigger. It does not rename or replace `Positions`, reclassify staff or overwrite existing payroll amounts. Existing approved allowances remain unchanged; pending allowance requests require an independent HR assessment before final approval.
