# Pay frameworks and position matrices

1. **Settings → Positions → Pay Frameworks → Frameworks**: a superadministrator adds/edits shared pay frameworks. Existing LEGACY, NEW_PAY and CUSTOM codes/IDs are retained. Framework codes are permanent; names are editable.
2. **Pay Frameworks → Job Matrices**: select a framework and enter the matrix code/version, name, currency, basic salary and effective dates. Add allowed titles, unique numbered pay steps (job allowance and optional basic salary override), and other allowances/benefits. Currency is shared across the matrix amounts. Benefit frequencies are Monthly, SixMonthly or Annually; a null amount is displayed as non-cash, never converted to a guessed amount.
3. **Manage Positions → Create position matrix**: an authorised organisation officer selects a framework/Job Matrix, one allowed title, approved staffing slots and effective dates. The form displays base salary and inherited benefits; it does not select an employee pay step. Saving atomically creates the organisation's `PF_PositionMatrix`, initial `PF_PositionMatrixHistory`, and the canonical `Positions` entry. Staff assignment continues to select from `Positions`.
4. **Staff workspace → Position** or staff onboarding: select the position and the employee Job pay step, then submit through the existing approval flow. The workspace displays its framework salary, step allowance and other benefits. Final approval rechecks the matrix and available staffing slots, then records the pay snapshot under the existing JobID.

## Permissions and history

Shared frameworks/Job Matrices are editable only by actual superadministrators. Current-organisation `Positions.Configure` enables local position-matrix creation; `Position.Details`/`Staff.Positions.Manage` allow catalogue reads. Organisation officers cannot alter a shared pay definition or another organisation's slots. The existing staff assignment/onboarding approval permissions are unchanged.

A Job Matrix is frozen once any position matrix uses it. Create a new code/version for changes rather than overwriting employment/pay history. Unused definitions can be edited, including their steps/titles/benefits. No destructive catalogue delete action is provided. A framework with active dependent matrices/positions cannot be disabled.

Both request submission and final assignment approval validate matrix ownership, active framework/title/step, and effective dates. Final approvals run within the existing serializable transaction and acquire a transaction-owned SQL matrix lock before rechecking slots. Capacity is maximum concurrent approved occupancy, rather than the count of all records overlapping a date range. This is shared across all position records linked to the matrix. Duplicate overlapping position matrices for a title are rejected, independently of employee steps.

New position matrices create one `Positions` record per approved slot, all with the same title and matrix link. Assignment selectors display the position ID to distinguish slots and exclude occupied positions. Every position permits only one overlapping approved job assignment, in addition to the overall matrix capacity check. Occupancy ends at the earlier of the assignment end and job termination date (exclusive); the position becomes available again without deleting its history. Submission and final approval recheck vacancy under a transaction-owned position lock. Historical records are preserved; earlier shared positions cannot receive another overlapping assignment. Pay steps continue to belong to employee jobs.

Position creation starts with framework buttons. Legacy CSC and Custom support direct position forms (and a matrix option when Job Matrices exist); other frameworks use the position matrix form. The Job Matrix selector lists all definitions in the selected framework, including inactive entries shown disabled, with matrix codes and ranks to distinguish versions. Refresh reloads the definitions.

**Change position** selects Framework → Position Matrix → Vacant position slot → Employee Job pay step. Each matrix shows available/approved slots; a matrix with no vacancy is disabled. Counts use current occupancy and the job termination date. Submission and final approval validate vacancy again for the requested date range, including future approved assignments, to protect against stale selectors.

**Assign position** is hidden while the staff member has a current approved position. Additional assignments are rejected by the API even if a different employment record or a future start date is selected. Overlapping approved position periods (including date extensions) are prohibited for the staff member in the organisation. Submission and approval acquire a staff-position transaction lock and repeat these checks. A configured Change position approval replaces the original assignment by closing it before the successor starts; it does not create concurrent positions.

An active staff position's **Job termination** action selects an existing Job Resignation, Retirement, Termination, Contract Expiration, Probation, Promotion or other job termination Request Type. It submits against that type's configured tenant/Job Type workflow and state transitions; it no longer creates a Staff Position Removal Request. The effective date is the first day no longer employed. Only final approval sets `Jobs.TerminatedDate`, closes that job's positions and pay-step periods, and releases its slots on the effective date. Requests are linked through `JobRequests` and the existing `SP_StaffPositionChangeRequests` audit payload (`Remove` discriminator retained for database compatibility). Legacy removal requests retain their original position-only meaning. No historical requests are reclassified.

An approved matrix assignment stores basic salary and job-allowance snapshots in `PF_JobStepHistory` and salary in `JobPositionBasicSalaries`. Position changes close the previous pay interval; effective-date changes synchronise the matching pay interval. No new JobID is created for the pay-step snapshot. There is no separate pay-step progression editor in this feature.

This feature configures the catalogue and assignments. It does not rewrite existing `Jobs.BasicSalary`, posted payroll, or legacy salary records. Matrix benefits are stored and inherited/displayed; this change does not automatically post those benefits to the allowance/deduction payroll subledger. Existing position allowance rules remain available separately.

## Database and deployment

Existing tables are reused: `PF_Frameworks`, `PF_JobMatrix`, `PF_JobMatrixTitles`, `PF_JobTitles`, `PF_JobMatrixSteps`, `PF_JobMatrixBenefits`, `PF_PositionMatrix`, `PF_PositionMatrixHistory`, `PF_JobStepHistory`, `Positions` and `JobPositionBasicSalaries`. Their existing keys and physical names are preserved. No new physical table is introduced.

The additive `PayFrameworkMatrixManagement` migration adds nullable `FrameworkID` and `CurrencyTypeID` to `PF_JobMatrix` with checked foreign keys. Existing rows are not assigned guessed values. A filtered unique index on `Positions.PositionMatrixID` ensures one canonical position per matrix; the migration stops on duplicates instead of deleting records. PF tables remain excluded from creation migrations and mapped against their existing schema. Apply the migration before restarting API/UI.

## Illustrated Job Matrix and employee step ownership

A Job Matrix is the profession/pay definition (for example Educational Counsellor), not an employee position or pay-step assignment. Its allowed titles can include Director and Educational Counsellor. HR creates the organisation position matrix using one allowed title and staffing slots; the same position can then be assigned to employees at different pay steps. Step selection is submitted with the employee's position/onboarding request and is visible to approvers. The approved step is stored against JobID in PF_JobStepHistory. The position name and slot allocation do not include the step.

The form additionally supports profession description, revision date, MISSCO code, skill level, public service rank, job family, institutional category, grade code, daily attendance benefit, licenses/training, qualification pathways, fields of study, work-experience areas and core duties. Classification name/code/skill snapshots are stored alongside the matrix; existing JobFamilyID/MisscoGroupID links are retained, and migration copies their referenced names/codes for display where available. Existing PF_JobMatrixQualifications and PF_JobMatrixDuties are reused for requirements. New requirements can be entered as full text including alternative pathways; previously stored structured records are never flattened, deleted or overwritten. Revising existing requirement text needs a new matrix version.

Migration JobMatrixProfilesAndEmployeeSteps adds nullable profile fields to PF_JobMatrix, employee step selections to SP_StaffPositionChangeRequests and SO_StaffOnboardingRequests, and makes the historical PF_PositionMatrix.JobMatrixStepID nullable. Old position-step references are retained for compatibility; new position matrices leave it null. Existing employee salary/step snapshots are not reassigned or deleted. No new physical tables are created.
## Reference dropdowns
PayFrameworkProfessionReferences reuses PF_JobFamilies and adds PF_Professions with source-edition/page provenance, task text, MISSCO code choices and editable example-title suggestions from the supplied 2019 Job Family Model. Job Matrix creation selects Job Family then Profession / Occupation. The server derives Name and validates the selected family/profession pair; the old Position / matrix name input is removed. Existing Job Matrix names and title records are preserved. Profile selections link through existing JobFamilyID and new nullable ProfessionID. Example titles are suggestions, not a closed eligibility list. This document predates the previously supplied 2023 position example; no claim is made that its titles are the complete current pay catalogue.

## Study field suggestions
PF_StudyFieldSuggestions stores the user-provided discipline examples linked to existing job families. The create/edit form offers a family-filtered selector that appends choices to the editable Fields of Study text. Custom text and previously saved matrix requirements remain valid and unchanged. The suggestions are not an exhaustive statutory eligibility catalogue and do not impose MNQF levels, institutional-category restrictions or exclusive agency eligibility. The user's Educational Services and ICT labels map to the existing 2019 Teaching Service and Information and Communications Service records without renaming historical families; the combined armed/protective examples are available under each existing family. Source metadata explicitly identifies the user-supplied examples rather than presenting the whole list as verified NPC policy.

## Experience area suggestions
PF_ExperienceAreaSuggestions stores the 16 user-supplied areas across higher education, school education, functional/corporate, health and ICT sectors. Optional JobFamilyId scopes academic/school areas to Teaching Service, health to Health Service and ICT to Information and Communications Service; null-family corporate examples are general suggestions. The selector groups by sector, appends full labels/descriptions without overwriting existing ExperienceAreas text, and permits custom wording. Source metadata records user-supplied examples. Verification guidance prompts review of employment dates, contract type, exact title, tasks and supporting documents. It is guidance, not an automated experience verification/recruitment decision or a universal post-qualification/rank rule. Matrix-specific requirements must be assessed separately.

## Structured licensing and qualification requirements
The Job Matrix editor now has structured credentials and qualification pathways. PF_CredentialRequirements stores credential name/type, issuing or recognising authority, Mandatory/Preferred/Conditional status, required condition text, accepted equivalents, validity months, renewal flag, optional training hours, evidence requirement, verification instructions and source reference. Suggested names/authorities are entry aids only; no licence/rank prerequisites are seeded automatically.
PF_QualificationPathways holds alternative routes (OR), each with relevant, post-qualification and managerial experience months, source reference and additional conditions. PF_PathwayQualifications stores the qualifications required together within a route (AND), optional MNQF level or inclusive level range, qualification description/type, field of study and recognised/accredited flag. Null levels support requirements such as basic literacy; a blank upper level means the exact selected level. No equivalency, qualification-type-to-level or rank-to-level rule is inferred.
Only existing shared-matrix administrators can configure these requirements. Loading returns IDs and a requirements-version hash. Saving verifies ownership of every ID, detects stale requirement edits, updates unused draft rows in place and soft-retires removed rows. Used matrices remain frozen. Copy as new version deep-copies requirements with new IDs. Operation logs capture before/after structured definitions. Legacy licensing text, PF_JobMatrixQualifications records and duties are preserved; this feature does not parse or replace them.
These are requirement definitions, not employee credentials or an automated recruitment/appointment screening engine. Issuance/expiry evidence, accreditation recognition, conditional applicability and actual applicant eligibility must still be verified separately. Requirements inherit the matrix effective dates/version. The additive StructuredJobMatrixRequirements migration creates the three PF_ tables with restrictive foreign keys and range/enum constraints; reversal is deliberately non-destructive.

## Entered software requirement presets
PF_ProfessionRequirementTemplates contains the source-linked Software and Applications Developers and Analysts presets for ranks 7, 8, 9 and 10, transcribed from https://www.finance.gov.mv/public/attachments/rgByNS1JiDA6AFetGJBJ8RE2pfzjYJGx54ouzm5e.pdf (pages 1, 3, 5 and 7). The licence/training requirement is conditional on the employing organisation's specified requirement; no mandatory named software council licence or certification is invented. Rank 10 routes are level 10 + 4 years, level 9 + 8 years, or level 7/8 + 12 years; rank 9 routes are level 10, level 9 + 4 years, or level 7/8 + 8 years; rank 8 routes are level 9 or level 7/8 + 4 years; rank 7 requires level 7/8. These are English working transcriptions with the official Dhivehi source retained. Post-qualification/managerial minimums, expiry periods and training hours are not inferred.
Select the software profession and rank in the matrix form. Blank notes and structured requirements populate from the preset; the explicit Fill blank requirements from source button is also available. HR-entered values are never replaced. When rank changes, untouched auto-filled values refresh to the new source; manually edited values remain. This import creates reference presets only: existing matrices (including the unrelated test row), positions, salary amounts and employee records remain unchanged. Matrix effective dates and financial amounts must still be configured and saved explicitly.
