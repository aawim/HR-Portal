# Communication Hub development status

The projects belong to `HRM.sln`. Telegram, Facebook Pages, Teams Workflows and WhatsApp approved-template transports are implemented. Facebook Messenger remains unavailable. Automated transport tests mock HTTP; they do not certify a real provider account. Full HRM workflow SQL integration and live-provider verification remain outstanding.

## Database placement

Administration at `/admin/settings/communications` requires active, approved Admin Portal admission bound to the account's current tenant. This applies to Tenant Administrators too. Within that tenant, the account must have Tenant Administrator authority (`Admin` permission or organisation-admin authority) or the explicit `Communication.Manage` permission. Platform administrator status alone does not bypass these checks. The permission is registered in the Roles & Permissions canonical catalog and Communication Hub area map; open permission definitions after deploying to materialize it, enable it in the tenant's permission ceiling, then assign it to delegated accounts/roles. No accounts or tenants are automatically granted this permission. Workflow reviewers continue using their assigned-reviewer authorization on `/online/communication-approvals`.

Use the same HRM SQL Server database and `HrmTeContext` as the API. Communication data uses `CM_` physical tables with normal foreign keys to HRM organisations, requests and jobs. This keeps business events and approval-driven delivery release within the same transaction. The worker remains independently deployable. The separate `HRMCommunications` database is not used by this implementation. A future database split will require a durable event bridge and changes to those relationships; changing only the worker connection string is not sufficient.

## Worker configuration

Configure the worker's existing HRM SQL Server connection using `ConnectionStrings__DefaultConnection`. Provision credentials through the deployment secret store or protected environment; do not commit tokens to configuration files.

A connection in organisation 10 whose credential reference is `telegram-primary` resolves its bot token from `Communications__Organisations__10__Credentials__telegram-primary`. Existing deployments must move global credential entries to organisation-scoped entries before upgrading. The UI's **Verify bot** action calls Telegram `getMe` through HRM.Api and requires that reference to be configured securely in the API host as well. **Verify access** checks bot identity and chat posting permissions without sending. Worker secret configuration remains separate; permissions can change after verification.

Outbound sending is disabled by default. Set `Communications__OutboundEnabled=true` only after credentials, destinations and routing are verified. Connections, destinations and automation rules must also be explicitly enabled. Rules requiring approval create held message snapshots visible in the administration page. **Submit for approval** creates a central Request linked to the snapshot and starts the existing workflow engine in the same SQL transaction. Configure a request type named `Communication Announcement` and its organisation/Job Type flow and state transitions first. Set its view URL to `/online/communication-approvals`. The submitting administrator requires active approved employment. Missing setup rolls submission back.

## Announcement decisions

Assigned reviewers and submitters use `/online/communication-approvals`; notification links for the Communication Announcement request type open the specific request on this page. Reviewers do not need integration administrator rights. The server uses the shared workflow processor to enforce current assignments, independent approvers, sequential/All/Any/Quorum stage behaviour, allowed request-state transitions and workflow audit records. Submitters can cancel their own pending request. Rejection and cancellation require a comment. Duplicate, stale and closed decisions are rejected.

Only final approval marks the saved message Approved and creates one Pending delivery to the saved destination, within the same SQL transaction as the workflow decision. Intermediate approvals do not create deliveries. Release rechecks organisation, source publication/audience, expiry and destination availability. Destination ID, connection ID and external chat ID are snapshotted when the held message is created; changed or missing snapshots prevent release. Older held messages lacking those fields must be recreated. Reject/cancel marks the held message accordingly and creates no delivery. The worker still observes its outbound switch and rechecks source/destination eligibility before sending.

Workflow tests use EF InMemory to verify business behaviour. The opt-in SQL test applies the actual communication scripts twice, preserves a pre-upgrade message, checks rollback and uniqueness, and races two database claims. It uses only minimal HRM boundary tables in its disposable database; it does not prove the complete HRM workflow or worker process lifecycle.

Run that test on local `.\SQLEXPRESS` with an account allowed to create databases: set `DHR_COMMS_SQL_TESTS=1` and run `dotnet test Tests/HRM.Api.UnitTests/HRM.Api.UnitTests.csproj --filter FullyQualifiedName~CommunicationSqlIntegrationTests --artifacts-path tmp/comms-verify2`. The test creates a generated `DHR_CommsTest_...` database and drops only that database after closing its connections. It is skipped by default. No real provider messages are sent.

For an explicit delivery test, select **Send test** on a saved destination and confirm the named destination. This queues a fixed test announcement through the worker; it does not call Telegram synchronously from the API. The destination and connection must be enabled. Requests are limited to one per minute per destination and become ineligible after ten minutes. No automation rule is required for this explicit test; the worker's global outbound switch still applies. Follow the result in delivery history. No live test has been executed as part of automated verification.

Set `Communications__OutboundEnabled=false` and restart the worker to stop new sends. A request already accepted by the provider cannot be recalled. Internal HRM notifications are not controlled by this switch.

Routing continues while outbound sending is disabled: eligible events can create pending deliveries, which will send when the switch is enabled. Review the queue before enabling. Events with no eligible rule are marked processed. Pending deliveries expire after `Communications:DeliveryMaxAgeHours` (default 24, range 1–168). Sends interrupted for more than ten minutes are marked failed with `IndeterminateWorkerInterruption`; review these rather than resetting them blindly.

## Additional platform setup

Use the platform selector at `/admin/settings/communications` to save integrations, destinations and rules. Tokens and signed webhook URLs belong only in organisation-scoped server secrets. The UI stores references, not credentials. Keep outbound disabled during setup.

- Facebook Pages: provision a Page access token with publishing permissions. Set `Communications__Meta__GraphApiVersion` to a supported version such as `v23.0` after checking your Meta app. Destination is the numeric Page ID. Only organisation-wide events explicitly marked Public qualify; public status is rechecked before approval release and sending. All Facebook rules require manual approval.
- Teams: provision a Teams Workflow that accepts the adaptive-card message payload. Store its signed Power Automate/Logic Apps URL as the credential. Use `workflow` as destination ID. Only HTTPS workflow hosts are accepted; redirects are disabled. Maintain a service owner/co-owner so the workflow survives staff changes.
- WhatsApp: provision a Business Platform access token, phone-number ID and approved template containing exactly one positional text body parameter. Save its approved language code with the integration. Destination is an international number and employee ID. Record employee opt-in evidence before activating. Unchecking consent deactivates delivery and preserves a revocation record. Each send rechecks consent, current employment and schedule version. Message parameters are limited to 1024 characters. Use separate integrations for different approved template languages.

Scoped schedule changes queue private employee events transactionally with existing in-app notifications. Pending changes to the same scope/job are coalesced for two minutes. WhatsApp is the only supported private schedule transport. Configure one rule per employee destination. English and optional Dhivehi rule bodies are versioned; the selected rendered body, destination, provider configuration and template version are saved with each message.

Deploy the worker as a supervised console process under a dedicated service account with access to the same HRM database and protected secret configuration. Use a process supervisor/Windows scheduled startup task appropriate to your deployment. Set a unique `Communications__WorkerInstanceId` per worker (defaults to the machine name). Each successful cycle updates `CM_WorkerHeartbeats`; the admin page reports heartbeat freshness and tenant-scoped Pending/Failed queue counts. Capture worker error logs and restart on failure. Apply all embedded `20261121_Communication*.sql` scripts in their bootstrap order using a deployment account before reducing runtime database permissions. All scripts are additive and idempotent. To roll back sending, disable outbound and restart; retain new columns/tables and queue records rather than dropping data.

## Current limitations

The router processes every enabled rule with an explicitly selected destination. Each rule has one destination. Organisation announcements require an organisation-wide audience; department/team/excluded audiences are skipped. Private scoped schedule messages require a matching employee WhatsApp destination with active consent. Individual schedule overrides, roster publication, holiday/duty-specific hooks, provider receipt webhooks, Messenger, queue dashboards and native service-host integration remain future work. A successful send means provider acceptance, not employee delivery/read confirmation. Delivery history currently shows the latest 50 attempts.

Build verification uses `--artifacts-path tmp/comms-verify2` to avoid access-denied errors in existing project `obj` files. Full-workflow SQL concurrency, production deployment and end-to-end business flows still require testing before production use.
